# Professional runtime audit (before implementation)

Audit date: 2026-09-10. This is the existing, dirty authoritative checkout; pre-existing changes are preserved. Production was not inspected or changed.

1. **Root cause:** `prebuild` runs `scripts/generate-marketplace-data.ts`, which reads Supabase and writes `.generated/marketplace-data.json` and `public/marketplace-data.json`. `lib/marketplace.ts` reads the generated file with `fs`, wrapped in React render memoization. Rebuilding is the only way those bytes change. The generator silently reuses the previous snapshot on fetch failure. English and localized professional routes also set `dynamicParams = false` and enumerate mutable profile slugs in `generateStaticParams`, so newly approved slugs cannot resolve without a build. Professional sitemap entries are generated from the same snapshot. This is a source-data problem, not merely a missing cache purge.
2. **Authority:** marketplace Supabase (`Elevare-Prod`, committed ref `cnfqpfynjpwlzdtblzps`), legacy backend tables `trainer_profiles`, `users`, matching, services, locations, certifications and trust checks. `professional` remains the application entity. Existing v2/international/trust views provide projections but require a stricter consolidated runtime contract. No manually maintained professional seed should be a runtime fallback.
3. **Public surfaces:** `/`, `/es/`, `/pt-br/`; `/professionals/` and localized equivalents; shared `/professionals/[slug]/` profile/category routes; directory filters/search/cards, location filters (no standalone location route), guided matching, related professionals, saved-professional/account/inquiry directory lookups, concierge candidate/shortlist RPCs, profile metadata/Open Graph/JSON-LD, and `/sitemaps/professionals.xml`. Client components fetch `/marketplace-data.json` directly.
4. **Mutation paths:** profile editor writes users/photo, trainer_profiles, trainer_services, trainer_locations, trainer_service_offerings, certifications, and review-submission RPC; retention availability and confirmation RPCs; insurance submissions; separate admin approval/rejection/publication/suspension and trust verification; deletion/account deactivation; derived matching updates; expiration jobs. Admin source is not present here. Database triggers are the only local coverage point shared by every writer.
5. **Cache behavior:** installed Next.js **16.3.1**, App Router, React 19.2.5. Current `next.config.ts` is server-capable (no export); README is outdated. Vercel uses the Next.js framework without an output override. No marketplace `unstable_cache`, tagged fetch, route revalidation, or public Realtime subscription. React `cache` deduplicates file reads during a render; it does not reload deployed files. Unrelated catalog static params and robots `force-static` are legitimate. No middleware/proxy affecting this flow was found.
6. **Revalidation:** none for professional data. `.github/workflows/vercel-refresh.yml` calls a deploy hook daily, also supporting other generated datasets. No existing professional database webhook or purge endpoint was found. Approval-email and trust-notification outboxes serve notifications, not website caches; do not repurpose their delivery semantics.
7. **Draft/publication:** existing field-triggered unpublication model, no parallel published revision table. Most content edits, including bio/prices/languages/services/location/categories, require re-review and set live=false/pending. Material edits must retain that behavior. Existing availability/confirmation security-definer RPCs are the permitted immediate operations and already compare updated_at. Related-table saves currently unpublish even on unchanged writes. Credential material-change triggers reset verified state and write trust audit history. Full editor saves lack atomicity and concurrency protection.
8. **Environments:** browser writes use NEXT_PUBLIC_SECOND_SUPABASE_URL; generator prefers SECOND_SUPABASE_URL, while server helper prefers NEXT_PUBLIC_SECOND_SUPABASE_URL. Differing settings could read/write different projects. There is no local .env with test credentials. No production values were inspected, so production consistency is unverified. Docker is installed but its daemon is unavailable; base users/trainer schema is external to the migration history. Do not apply local migrations against production to unblock testing.
9. **Minimal fix:** reuse mapper and review rules; replace generated reads with a restricted server-side Supabase public projection and tagged caches; allow runtime slugs; serve compatibility JSON and sitemap at runtime; use per-professional coalescing invalidation outbox with authoritative old/new membership and slug history; authenticated website save/retry and internal invalidation endpoints; atomic version-checked editor RPC; external delivery adapter. Fail closed on missing configuration or missing security migrations. Preserve static unrelated pages. No hosting/export conversion is necessary.
10. **Expected changes:** `lib/marketplace.ts`; extracted mapper/server/cache/invalidation helpers; professional and localized route params; new runtime marketplace JSON/sitemap/API routes; generator/package scripts; editor and retention components; localized propagation/conflict messages; additive `supabase/migrations/20260910120000_professional_runtime_publication.sql`; optional dormant Supabase delivery function/config; runtime/security/production integration tests; environment examples; README and operations documentation. No production migration, push, deployment, or production-data write is authorized.

Security findings to address: old international projection includes exact coordinates/postcode; existing eligibility omits reliability suspension; optional trust fetch falls back to legacy credential claims. Runtime reads must require the new restricted projection, not silently fall back to these older paths. Stable professional/service IDs needed for consultation/save/report operations remain; unrelated account/auth/location/credential UUIDs do not belong in the public contract.

Completion gate: a production-mode local Next.js cache test is necessary, and a real disposable Supabase mutation/RLS integration test is also necessary. A mock protocol server can test Next.js cache behavior but cannot prove Supabase authorization or deployed schema correctness. Missing infrastructure must remain a reported limitation, not a passing test.

Implementation follow-up (2026-09-11): Docker became available. The final tests use isolated Supabase Postgres and PostgREST with a synthetic contract fixture, actual migration, actual authenticated mutation endpoints and production `next start`. The complete historical/legal baseline remains external, so staging rehearsal is still required. Production testing revealed a deferred-purge/in-flight-cache-fill race; immutable database generation keys now prevent a new request from selecting an old record. The full-editor browser test also exposed indefinite database retries when a stale edit used SQLSTATE 40001; stale edit tokens now raise an application error that the API maps to HTTP 409. See the operations guide and final report for the implemented flow, proof and limits.
